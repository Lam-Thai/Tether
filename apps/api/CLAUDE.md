# apps/api

FastAPI backend. See the root `CLAUDE.md` for the hard rules and the layer map (`api / core / schemas / services / repositories / models / integrations / tests`) — this file only adds conventions specific to this app.

## Layout

```
main.py              # entrypoint: `from core.app import create_app; app = create_app()`
core/                 # settings, db engine/session, app factory, error envelope + handlers
schemas/              # Pydantic request/response models
services/             # business logic (deep modules) — no FastAPI or SQLAlchemy imports
repositories/         # the only layer that queries the DB
models/               # SQLAlchemy ORM models + shared declarative Base
integrations/         # external provider clients, each behind a port + in-memory fake (clerk/, stripe/, llm/, tts/, google_calendar/, twilio/)
api/                  # routers; `api/health.py` mounted at app root, `api/v1/` for everything else
migrations/           # async Alembic environment
tests/                # mirrors the layers above
```

## Auth and tenancy

- `core/auth.py`: `verify_principal(token, resolve_signing_key, issuer, authorized_parties) -> Principal` is the only function that knows a Clerk token's claim shape (`sub`, `email`, `azp`). Every failure — bad signature, expired, wrong issuer, unrecognized `azp`, unreachable JWKS — maps to the same `AuthError` (401). `resolve_signing_key` is the `integrations/clerk` port; tests pass an in-memory fake backed by a real RSA keypair instead of a live JWKS fetch.
- `core/tenant.py`: `get_tenant` is the `TenantContext` FastAPI dependency — `get_tenant() -> Tenant(user, business)`. It verifies the bearer token, just-in-time upserts the `users` row from the Clerk subject, and resolves `business` from `owner_id` only. `business` is `None` before onboarding. Every business-scoped router depends on `Tenant`, never on a raw `business_id` from the client.
- `repositories/base.py`: the `BusinessScopedRepository` pattern from issue #3, implemented as a function (`business_scoped_select(model, business_id)`) rather than a class, to match this repo's function-style repositories (see `repositories/health.py`). Every domain repository with a `business_id` column builds its queries on this, always called with `tenant.business.id` — never a client-supplied id.
- Services stay free of SQLAlchemy imports by taking repository functions pre-bound to the session via `functools.partial` (see `services/business.py` / `api/v1/business.py`), the same pattern `services/health.py` already uses for `check_db`.

## DB sessions

`core.db` builds one async SQLAlchemy engine per process (`NullPool`, `pool_pre_ping=True`, 5s statement timeout — serverless-safe, since Neon's own pooler handles connection pooling at the proxy layer) and exposes `get_session()` as a FastAPI dependency that yields one session per request. A plain `postgresql://` URL (what Neon's UI gives you) is rewritten to `postgresql+asyncpg://` automatically.

## Error model

Every error response is the same envelope: `{"error": {"code": "<snake_case_code>", "message": "<human message>"}}`. `core/errors.py` defines `AppError` (status_code + code class attrs) as the base for domain errors, and registers handlers for `AppError`, Starlette's `HTTPException`, `RequestValidationError` (422, `validation_error`), and a catch-all (500, `internal_error` — the real exception is logged server-side via `logging`, never leaked to the client). Add new domain error types by subclassing `AppError`; don't invent a new envelope shape.

## Repository pattern

`repositories/` is the only layer that queries the DB. The health check (`repositories/health.py`) is a connectivity probe with no tenant data, so it doesn't take a `business_id`. `repositories/users.py` and `repositories/business.py` are the two exceptions that establish identity before a `Tenant` exists (scoped by `external_auth_id` / `owner_id`); every later domain table with its own `business_id` column scopes through `repositories/base.py` instead (see "Auth and tenancy" above).

## Routing convention

Liveness/infra checks (`/health`) mount unversioned at the app root — they're not business endpoints. Everything else mounts under `/api/v1` (see `api/v1/router.py`, currently empty). Routers only parse the request, call one service method, and shape the response — no business logic or direct DB access in `api/`.

## Alembic

Async environment (`migrations/env.py`) reads `settings.database_url` through the same normalization `core.db` uses — never a hardcoded URL in `alembic.ini`. Workflow: change a SQLAlchemy model → `uv run alembic revision --autogenerate -m "..."` → hand-review the generated SQL (indexes on `business_id`, FKs, unique constraints, timestamps) → write and test the `downgrade()`. Never call `alembic upgrade head` from application startup code; it's a separate, explicit command.

## Billing and entitlement

- `services/billing.py` is the deep module (`start_checkout`, `sync_checkout`, `apply_event`, `open_portal`, `get_plan`, `summarize`, `access_for`). Stripe sits behind `integrations/stripe/port.py` (`BillingGateway`) with a real adapter (`adapter.py`) and `FakeBillingGateway` (`fake.py`); no Stripe SDK type leaves that package.
- **Every business-feature router (Slice 4 onwards) depends on `core.billing.get_entitled_tenant`, not `get_tenant`.** It returns 402 `subscription_required` unless the business is `trialing`, `active` or `past_due`. Only onboarding, `/me`, `/business` and `/billing/*` stay on `get_tenant`.
- Stripe is the source of truth. The webhook (`POST /api/v1/webhooks/stripe`, raw-body signature check, `stripe_events` dedupe) and the return-page sync both **re-fetch** the subscription from Stripe instead of trusting payloads, under a per-business row lock (`repositories/billing.py`).
- Local webhooks: `stripe listen --forward-to localhost:8000/api/v1/webhooks/stripe`, then put the printed `whsec_...` in `STRIPE_WEBHOOK_SECRET`. Opt-in live smoke test: `STRIPE_LIVE_TESTS=1 uv run pytest -m live -n 0` (with a local `DATABASE_URL` and `ENVIRONMENT=local`).
- No card data ever reaches Tether: Checkout and the Billing Portal are Stripe-hosted, and the web app holds no Stripe key at all.

## Google Calendar

- Modules: `integrations/google_calendar/` (`port.py` `GoogleCalendarApi` + dataclasses + `GoogleApiError`, `client.py` `HttpGoogleCalendarApi` over httpx with no Google SDK, `fake.py` `FakeGoogleCalendarApi`), `services/token_vault.py` `TokenVault`, `services/oauth_state.py` `OAuthStateSigner`, `services/calendar.py` (`CalendarGateway` / `GoogleCalendarGateway`, `CalendarConnections`), `repositories/calendar.py` `SqlCalendarStore`, `core/calendar.py` (dependencies), `api/v1/calendar.py`, table `calendar_connections` (one row per business).
- Flow: `GET /calendar/connect` returns `{url}` (state + PKCE S256, `access_type=offline`, `prompt=consent`, `include_granted_scopes=false`). Google redirects to the WEB page, which POSTs `{code, state}` to `POST /calendar/callback` with the owner's bearer. Then `GET /calendar/calendars` (owner-owned calendars only), `PATCH /calendar {calendar_id}` -> `connected`, `GET /calendar/status`, `DELETE /calendar`. Status is `not_connected | needs_selection | connected | reconnect_needed`; `last_error` is always a fixed code (`auth_revoked`, `token_unreadable`, `unavailable`, `calendar_missing`). Errors: `invalid_oauth_state`, `calendar_scopes_missing`, `calendar_grant_incomplete` (400), `calendar_not_connected`, `calendar_not_found` (404), `calendar_reconnect_needed` (409), `calendar_unavailable`, `calendar_not_configured` (503). Every route is on `get_entitled_tenant`; only `GET /status` works while unconfigured (it answers from the DB and skips the live probe).
- Scopes are minimal: `calendar.calendarlist.readonly`, `calendar.freebusy`, `calendar.events.owned`. A grant missing any (or without a refresh token) is rejected with a 400 and NOT revoked; a reconnect simply overwrites the stored token and never revokes the old one. Google grants are per Google account and OAuth client, and Google's revoke endpoint kills the whole grant, so revoking a rejected or replaced token would also kill a working one (a reconnect loop). The same reason means two Tether businesses connected to the SAME Google account share a grant: disconnecting one revokes the other's access, which surfaces there as `reconnect_needed`.
- Security: the refresh token exists in plaintext only inside a request. At rest it is AES-256-GCM (`TokenVault`), sealed with the active key, its id stored next to it, and bound by AAD to `calendar:<business_id>` so a ciphertext moved to another row fails to open. Rotation: put a new `key_id:key` FIRST in `CALENDAR_TOKEN_KEYS`, keep the old ones; old rows still decrypt, and `status` re-seals a row under the active key (`store.reseal`) after its next SUCCESSFUL live probe, so drop the old key only once `calendar_connections.token_key_id` shows nothing on it. No access token is ever stored. An unknown key or tampered ciphertext is `reconnect_needed` / `token_unreadable`, never a 500. `state` is a short-lived HS256 JWT (aud, business, user, nonce) and `/callback` rejects a state whose business or user differs from the bearer's (login CSRF). PKCE verifier = HMAC(secret, nonce), so no server-side state. Secrets only travel in POST form bodies or the `Authorization` header, never in a URL (httpx logs URLs); `GoogleApiError` messages are fixed reason codes; `OAuthGrant`/`AccessToken` reprs hide tokens; no log line, response or `last_error` contains provider text.
- Metering: every Google call, including each token refresh, is `retry_bounded(CALENDAR_RETRY: 2 attempts)` around `usage.metered(CALENDAR_CALL, business_id=...)` (`services/calendar.metered_google_call`), retrying only `GoogleApiError.retryable`. The one-time code exchange uses `EXCHANGE_ONCE` (a code is single-use). A reached limit or an unreadable usage store becomes `CalendarUnavailableError` with no provider call, never retried. A gateway call that hits `CalendarAuthRevokedError` makes `CalendarConnections` mark `reconnect_needed` and `store.checkpoint()` BEFORE raising 409, so the state survives the failing request (the same commit-then-raise idea as billing, done in the service). The service also checkpoints before every provider call so no transaction is held across it.
- Lost updates: `status`, `select` and `reseal` read the row, call Google, then write. `set_selection`, `mark_status` and `reseal` are conditional (`WHERE business_id = :b AND updated_at = :seen_updated_at`; `updated_at` comes from `clock_timestamp()` so it changes on every write) and, when nothing matched, return the current row (or `None`) without changing it. So a reconnect or disconnect in another tab is never overwritten: `status` reports whatever is current, `select` answers 404 `calendar_not_connected` (gone) or 409 `calendar_reconnect_needed` (changed), and a re-seal that lost writes nothing.
- Code exchange errors: only Google's `invalid_grant` (a bad, used or expired code) is 400 `invalid_oauth_state`; any other failure (a bad client secret is `invalid_client`, which is not an owner problem and never flips a connection to `reconnect_needed`) is 503 `calendar_unavailable`. `CalendarError.detail` carries the provider's fixed reason code for this.
- Status probing: `status` calls Google (refresh + list) only for `needs_selection`/`connected` rows whose `last_synced_at` is older than `CALENDAR_STATUS_CHECK_SECONDS`; revoked -> `reconnect_needed`, an outage keeps the status and sets `last_error=unavailable`, a missing chosen calendar -> `needs_selection` + `calendar_missing`.
- Disconnect always deletes the stored token. It revokes at Google first; `{"revoked": false}` means Google could not confirm (transient failure or unreadable token) and the UI links https://myaccount.google.com/permissions. Already revoked counts as `true`.
- Availability (slice 10) reads busy time only through `CalendarConnections.free_busy(business_id, TimeWindow)`: unconfigured, no row or no chosen calendar is `CalendarNotSelectedError`; a `reconnect_needed` row is `CalendarAuthRevokedError` with no Google call; a grant revoked during the call is marked `reconnect_needed` and committed before re-raising; a chosen calendar that is gone becomes `needs_selection` + `calendar_missing`; anything else is a `CalendarError` (unavailable). It commits before calling Google, so a caller must not hold a savepoint around it.
- Slices 10/11 (booking): depend on `CalendarGateway`, never on the raw API. Build a `CalendarConnection` from the row with `services.calendar.connection_from_row(row)` (the row from `SqlCalendarStore.get(business_id)`, `business_id` from `TenantContext`), then `free_busy(conn, TimeWindow)`, `create_event(conn, EventDraft, idempotency_key)` (the Google event id is derived from the key, so a retry cannot double-book) and `cancel_event(conn, event_id)`. Handle `CalendarAuthRevokedError` (tell the owner to reconnect, never confirm a booking), `CalendarUnavailableError` (safe fallback, nothing confirmed), `CalendarNotFoundError`, `CalendarNotSelectedError`. Only tell a customer a booking exists after `create_event` returns. Slice 11 reaches these through `CalendarConnections.create_event` / `cancel_event` (see "Booking (slice 11)").
- Tests: the `calendar` fixture (`tests/conftest.py`, `CalendarHarness`) wires `FakeGoogleCalendarApi`, a vault on a random key and a test state secret as the app's dependencies and marks the feature configured; without it the app is unconfigured. The fake is scriptable (`issue_grant(scopes=, calendars=, refresh_token=)`, `add_busy`, `set_calendars`, `revoke_externally`, `fail_next(op, GoogleApiError(...), times=)`) and records `calls`, `revoked`, `events(refresh)`. Gateway tests compose `GoogleCalendarGateway(fake, vault, guard(MemoryUsageStore()))` (`tests/services/test_calendar_gateway.py`). The real adapter is tested over `httpx.MockTransport` (`tests/integrations/test_google_calendar_adapter.py`). There is no live Google test: the Google Cloud app stays in Testing mode, whose refresh tokens expire after 7 days (that surfaces as `reconnect_needed`).

## Conversation engine and Gemini

- `services/conversation.py` `ConversationEngine` is the single entry point for every conversation turn (`handle_turn`, `end`, `transcript`); the voice slices reuse it with a Twilio adapter. It is stateless between calls: messages, entities, failures and fallback markers live in `interactions` / `interaction_messages` (`state` JSONB), never in process memory.
- Gemini proposes, the backend validates: the adapter returns raw text (`ModelReply`), the engine parses it against `schemas/agent_turn.AgentTurn`. Invalid output (bad JSON, schema miss, blank reply, a tool not in `services/tools.ToolRegistry`) gets exactly one retry, then a fixed fallback line; provider failure (after `LLM_RETRY`'s 2 attempts) or the per-turn deadline gets the provider fallback. A reached usage limit gets `quota_fallback(business)` (the business's own phone/email, no promised callback), makes zero model calls, sets `state.requires_human`, and is never retried. The two fallback constants plus `quota_fallback`, `no_info_fallback`, `availability_fallback` and `booking_fallback` in `services/conversation.py` are the only agent text that doesn't come from the model or the owner's greeting. Failures are recorded on the interaction as fixed reason codes, never raw model or customer text.
- Tool loop: tool requests travel inside the JSON reply (`AgentTurn.tool_calls`; Gemini 2.5 can't combine structured output with native function calling). A reply with tool calls is never shown: `services/tools.ToolExecutor` validates each call against the tool's Pydantic args model (`rejected` and never run on a miss), runs it, and writes an `interaction_operations` row for every call; then the engine checkpoints and rebuilds the request with FAQ RESULTS / TOOL RESULTS in the system instruction. At most `MAX_TOOL_ROUNDS` (3) rounds of `MAX_CALLS_PER_ROUND` (3) calls; a model still asking after that gets `no_info_fallback`. So one turn makes at most 5 model calls, all under the one turn deadline (which cancels model calls only, never DB work). The per-request registry is built in `core/conversation.py`; adding a tool is one registration (`gemini-tool` skill). A tool's `ToolResult.state` is merged into `interactions.state` only when the turn's reply is shown (a fallback sets those keys to null instead), and `ToolResult.requires_human` flags the interaction. A tool that calls a provider is `Tool(isolated=False)`: the executor doesn't wrap it in the savepoint (it must commit before the provider call), so it opens its own `savepoint()` around its DB reads; the executor commits before running it and calls `store.rollback()` if it raises, so the failure is still logged instead of a 500. Within a turn, a tool's null state value doesn't erase a non-null one an earlier call set (a later "nothing found" keeps the offer).
- Where facts come from: FAQs only through `search_faq` → `services/knowledge.KnowledgeBase.relevant` (active FAQs only; all of them when a business has ≤ `limit`, otherwise OR-semantics Postgres FTS on the generated `faqs.search_vector`; no match is `[]`, never the whole table). Services only through `get_services` (a list, or `find_service` → found / ambiguous / not_found). Profile (BUSINESS FACTS, incl. currency) and hours (BUSINESS HOURS: today in the business timezone, the weekly hours, the next 7 days' windows) are in every prompt, read through `BusinessDirectory` each turn; `get_business_info` covers later dates.
- Grounding (`services/grounding.py`, fresh `TurnEvidence` per turn): every cited source must be valid *this* turn (an FAQ or service id a tool returned, `business_hours` only when hours are listed, `business_profile` always). Intents in `GROUNDED_INTENTS` need a source of an `ACCEPTED_SOURCES` kind (FAQ→FAQ; BUSINESS_HOURS→hours or FAQ; LOCATION→profile or FAQ; PRICE_INQUIRY→service or FAQ; a PRICE_INQUIRY may cite nothing only after a `not_found`/`ambiguous` lookup). Every money amount and duration in the reply, whatever the intent, must numerically equal a price/duration of a service returned this turn or one in a retrieved FAQ answer. Any failure → `no_info_fallback(business)` (the business's contacts, no callback), `state.requires_human`, a fixed reason code. The guard checks ids, numbers and times of day, not wording. Times (`clock_times`, strict on purpose since a missed form is an unchecked time: "2:30 PM", "14:30", "2.30pm", "14h30", "2pm", "noon", "two thirty", "half past two", "twenty to three", "half two", "2 in the afternoon", "eight tonight", "at 2", "around 2", "at 1430", ranges "9-5" / "from 9 until 5" / "2-4 pm"; a bare "at N" only before a time-ish word, so "at 1 Main St" is an address): every one must be a start time of the LAST offer `check_availability` made this turn (a later offer replaces an earlier one, so a time is only valid for the date and service it was offered for). With no offer this turn, a reply may repeat a time from the offer the customer heard last turn (`state.offered_slots`, also shown in the prompt as TIMES OFFERED IN YOUR LAST REPLY), and a `HOURS_TIME_INTENTS` reply (BUSINESS_HOURS, FAQ, LOCATION) without offer wording ("available", "book", "works", "I have", ...) may state opening/closing times shown this turn and times in a retrieved FAQ answer. Intent is the model's own label, which is why offer wording, not intent alone, decides. A miss is `unverified_time`: one regeneration with `TIME_CORRECTION` in the request (sharing the single invalid-output retry), then `availability_fallback(business)` + `requires_human`. Known limit: the guard compares times of day, not dates, so it relies on last-offer-wins; a structured `offered_slot_ids` field in `AgentTurn` would be the stronger design. Each tool executor runs inside `store.savepoint()`, so one that fails on a DB error rolls back only its own work and is still logged as `failed`.
- Transactions: the engine calls `store.checkpoint()` (a commit) before every model call, so no transaction or connection is held across it. The interaction row lock (`FOR UPDATE`, 3s `lock_timeout` → 409 `interaction_busy`) is taken only after the call, to allocate `sequence_number` and merge state.
- `services/prompt_builder.build(PromptContext)` puts platform rules first; owner settings and conversation-extracted data go after them inside delimited blocks, through the builder's sanitizers. Never interpolate owner or customer text into the system instruction any other way. Owner text (FAQ answers, service names and descriptions, business fields) reaches the model only through these sanitizers or inside JSON tool results.
- `integrations/llm/`: `LLMClient` port, `GeminiClient` (google-genai), `FakeLLMClient` (tests script replies turn by turn with `queue(...)` and `agent_turn(...)`; `len(llm.requests)` is the provider call count; fake tokens are 100 in / 20 out). The Gemini structured-output schema (`response_schema_for_gemini`) is hand-built and separate from `AgentTurn`: change both together. Adapter policy: **one attempt per `generate`**, failures raise `LLMUnavailableError(retryable=...)` (retryable only for timeouts, transport errors, 408, 429 and 5xx; a 429 also sets `rate_limited` and, from Google's `RetryInfo`, `retry_after_seconds`; the error message itself is never kept); blocked/empty/truncated replies are not retryable; token counts come from `usage_metadata` (thinking counts as output); never log prompts or model output. The engine retries with `retry_bounded(..., LLM_RETRY, is_retryable)` around `UsageGuard.metered`.
- Opt-in live smoke test against real Gemini: `ENVIRONMENT=local DATABASE_URL=<local postgres> GEMINI_API_KEY=... uv run pytest -m live -n 0` (the test guard refuses production settings and remote databases). Measuring behavior across many utterances is the eval harness's job, not this smoke test's.

## Availability (slice 10)

- Deep module `services/availability.py` `AvailabilityService.find_slots(tenant, service_id, SlotPreference(date, time_of_day?, around?)) -> SlotOffer | NoAvailability | CalendarUnavailable` (unknown, inactive or foreign service: `ServiceNotFoundError`, 404). Every DB read first (inside the injected `savepoint`), then the backend's own date rules with no calendar call (`past_date`, `beyond_horizon`, `closed`, `hours_not_set`, `service_too_long`, `no_time_left` (today), `too_soon` (a later day still inside the minimum notice, with the earliest bookable date)), then `CalendarConnections.free_busy` over the opening window widened by the buffer (`not_connected`, `reconnect_needed`, `unavailable`, latency logged on `tether.availability`, a warning over 2 s), then `fully_booked` or an offer.
- The core is pure and exhaustively tested (`tests/services/test_availability_slots.py`): `compute_slots(windows, busy, duration, rules, now)` does all arithmetic in UTC and returns slots in the window's zone (DST safe), merges busy blocks widened by the buffer on BOTH sides, snaps starts to the interval grid anchored at opening time, and applies the minimum notice and the horizon (`now + max_days_ahead` days) as instants. One calendar is one chair: any busy block blocks. `choose_slots` offers at most 3: filtered by part of the day (morning < 12:00 <= afternoon < 17:00 <= evening), the nearest to `around`, else evenly spread; nothing in the preferred part falls back to the whole day (`matched_preference=False`).
- Booking rules: table `booking_rules` (one row per business, CHECKs match the settings bounds), `services/booking_rules.py`, `core/booking_rules.py` (`default_booking_rules` dependency, `SqlBookingRulesStore` in `core` because it speaks the service dataclass), `GET/PUT /api/v1/business/booking-rules` (entitled; `customized: false` until saved).
- Tool `check_availability` (`services/availability_tool.py`, `isolated=False`): args `service`, `appointment_date` (YYYY-MM-DD the model resolves from "Today ..., local time now HH:MM" in BUSINESS HOURS; "today"/"tomorrow" are resolved by `resolve_date`, anything else is rejected `invalid_date` with `expected` and `today` so the model can correct itself; the name is unique on purpose because `response_schema_for_gemini` drops the description of an argument name two tools share, and the first live eval showed the model then sending unusable dates), `time_of_day`, `around` (HH:MM). `offered_times` become `Evidence.slot_times` (the only times the reply may state) and `interactions.state.offered_slots` (`service_id`, `date`, `timezone`, `slots[{start,end}]`, `offered_at`), which slice 11 books from after re-checking; any other outcome sets `offered_slots` to null. `calendar_unavailable` sets `requires_human`.
- Owner preview: `GET /api/v1/calendar/availability?service_id=&date=` (entitled) returns `status`, `reason`, `slots` / `offered` (`start`, `end`, `label` HH:MM) for the same lookup; `core/calendar.get_clock` is overridable in tests. Endpoint tests: `tests/api/test_calendar_availability.py`; engine-level ones with a scripted busy source (`tests/services/fake_busy_source.py`): `tests/services/test_availability_engine.py`.

## Booking (slice 11)

- Deep module `services/booking.py` `BookingService.book(tenant, BookingRequest(interaction_id, service_id, date, start_time, customer_name, customer_phone?)) -> Confirmed(booking, replayed) | SlotTaken(alternatives) | Invalid(reason) | CalendarFailed(reason)`. Only `Confirmed` means a booking exists: the Google event was created AND the row is `confirmed`. Order: validate name/phone -> idempotency lookup (key `interaction:service:start_utc`; an active `confirmed` row is replayed with no second event, a `pending` one is `in_progress`) -> availability recheck through `AvailabilityService.find_slots` (start not among the day's free starts -> `SlotTaken` with the nearest offered alternatives; date rules -> `Invalid`; calendar unreadable -> `CalendarFailed`) -> reserve a `pending` row and COMMIT -> `CalendarConnections.create_event` (event id derived from the booking row id) -> `confirmed` + `calendar_event_id`, committed. The duration always comes from the stored service; `blocked_until` = end + the business's buffer; `timezone` snapshots the business's IANA zone, and summaries and confirmations render in it, so a later timezone change never moves the local time a customer was told.
- Zero double bookings is the database's job: table `bookings` (statuses `pending | confirmed | failed | cancelled | needs_reconciliation`), `ex_bookings_no_overlap` (`EXCLUDE USING gist (business_id =, tstzrange(start_time, blocked_until) &&) WHERE status IN ('pending','confirmed')`, needs `btree_gist`), partial unique `(business_id, idempotency_key)` over the same active statuses. `repositories/bookings.SqlBookingStore.reserve` returns `SlotConflict` / `KeyConflict` values (savepoint, constraint name in the error), never raises for a lost race. `reserve` and the stale sweep first take a per-business `pg_advisory_xact_lock` (until the service's commit right after, never across Google): concurrent inserts racing on an exclusion constraint otherwise DEADLOCK (one aborted with 40P01, not a constraint error; measured 9 in 25 runs of the concurrency test without it). One calendar is one chair: any overlap conflicts, whatever the service. `pending` rows older than `PENDING_TIMEOUT_SECONDS` (300, database time) are swept to `needs_reconciliation` before each reserve.
- Compensation: a create failure that may have reached Google (timeout, 5xx; not a usage limit, revoked grant or missing calendar) deletes the event by its derived id first; the row is `failed`, or `needs_reconciliation` if the delete couldn't be confirmed. An event created but not saved is cancelled (`failed`/`not_saved`) or `needs_reconciliation`. `needs_reconciliation` never blocks a slot here (Google's free/busy still shows the event if it exists); nothing reconciles it automatically yet.
- `CalendarConnections.create_event(business_id, draft, key)` / `cancel_event(business_id, event_id)` share `free_busy`'s rules (`_chosen_calendar` + `_on_chosen_calendar`: not configured/connected/selected -> `CalendarNotSelectedError`, revoked -> `reconnect_needed` committed before re-raising, commit before the Google call). `cancel_event` raises `CalendarNotFoundError` as is (already gone counts as undone).
- Tool `create_booking` (`services/booking_tool.py`, `isolated=False`): args `service`, `appointment_date` (the same `ServiceArg` / `AppointmentDateArg` aliases as `check_availability`, so Gemini's merged schema keeps their descriptions), `start_time` (HH:MM), `customer_name` (required, so a missing name is `rejected` and never runs), `customer_phone` (optional; voice will take it from caller ID). Results: `confirmed` (`Evidence.booking_confirmed`, the booked start as the only allowed time, `offered_slots` cleared), `slot_taken` (alternatives become the new offer, like `check_availability`), `invalid`, `ambiguous_service`, `service_not_found`, `booking_failed` (`requires_human`). The log gets ids, date, result and reason codes only.
- Booking guard (`services/grounding.booking_claims`): every reply, whatever its intent, may claim a booking ("you're booked", "I've booked you in", "your appointment is confirmed", "I have you down") only with `booking_confirmed` this turn, and may never claim a cancel/reschedule/move (no tool yet). Conditionals ("once you're booked"), someone else's booking ("that time is already booked") and a clause that asks (ends with `?` AND opens like a question: "Shall I have you down?") are not claims; a claim followed by a question ("You're booked - anything else?", "You're booked, anything else?") still is. Sentences are split into clauses at dashes and semicolons. A miss is `unconfirmed_booking`: one regeneration with `BOOKING_CORRECTION` (sharing the single retry), then `booking_fallback(business)` + `requires_human`.
- RESCHEDULE / CANCEL (MVP): the agent collects the name and which appointment, says the team will be notified, and points to the business's contacts; the escalation policy records a `change_request` escalation (slice 13). Real cancel/reschedule is a follow-up.
- `GET /api/v1/bookings?interaction_id=` (entitled): the conversation's booking attempts, oldest first (`id`, `service_name`, `start`/`end` in the business timezone, `date`, `label` HH:MM, `customer_name`, `status`); another business's interaction lists nothing. The test chat's side panel reads it. `core/booking.build_booking_service` builds the service for both this route and the engine; `core/calendar.get_clock` now also pins the conversation engine's clock in tests.
- Tests: `tests/services/test_booking.py` (the module, in memory: `memory_booking_store.MemoryBookingStore` with the schema's rules, `fake_booking_calendar.FakeBookingCalendar` with scriptable create/cancel failures), `test_booking_concurrency.py` (real Postgres, a barrier so every caller passes the recheck: exactly one `Confirmed`), `tests/repositories/test_bookings.py` (the constraints), `test_booking_engine.py` (the tool and the guard through the engine), `tests/api/test_bookings.py` (the demo end to end). `FakeGoogleCalendarApi` now reports created events as busy, like Google.

## Inbox and the interaction lifecycle (slice 12)

- Status is the lifecycle: `in_progress | completed | failed | abandoned` (`ended` in the API = `status != in_progress`). Outcome is what happened: `booked | failed | escalated | abandoned | answered`, NULL while in progress. Both are derived ONLY by `services/lifecycle.close_outcome(ClosingFacts, reason)` from backend records (a confirmed `bookings` row, a `create_booking` log row with `booking_failed`, the last agent message being a fallback, `state.requires_human`): `failed` = nothing booked and a booking failed or the last reply was a fallback; outcome precedence booked > failed > escalated > abandoned > answered. `interactions.intent` is the PRIMARY intent (`primary_intent` over `state.intents`, booking-type first), updated every turn.
- `InteractionLifecycle` (shared by every channel; voice reuses it): `end` locks, closes, COMMITS, then calls the summarizer (through `summarize_safely`: a failure there is logged as a code, the shared session is rolled back, and it never undoes the close; an already-closed interaction only gets a missing summary; callers copy tenant ids and the timezone into plain values first, since a rollback expires ORM objects). `abandon_idle(business_id)` closes this business's `in_progress` rows idle longer than `INTERACTION_IDLE_MINUTES` (`FOR UPDATE SKIP LOCKED`, at most 50 per call, `ended_at` = last activity) with a template summary and zero model calls. `build_conversation_engine(..., summarizer=None)` uses `NoSummarizer` so the eval harness doesn't pay for summaries; only `get_conversation_engine` passes the real one.
- Read model: `services/inbox.Inbox` (`list` sweeps idle rows first, then reads; `detail` lazily summarizes a closed interaction whose `summary` is NULL, via `lifecycle.summarize_safely`; `messages`) over the `InteractionQueries` port, implemented by `core/inbox.SqlInteractionQueries` (in `core` because it returns the service's dataclasses) on `repositories/interaction_queries.py`. Keyset pagination on `(started_at DESC, id DESC)` with an opaque cursor (malformed: 400 `invalid_cursor`). Filters AND together: `type` (`bookings` = booking intents or outcome booked; `faqs` = FAQ/hours/location/price intents; `escalations` = outcome escalated or `requires_human`; `failed` = status failed), `status`, `intent`, `from`/`to` (inclusive dates in the BUSINESS timezone; from > to is 422 `invalid_date_range`). Timeline labels come from `operation_label` (machine codes and short ids only, never free text).
- Routes (entitled tenant): `GET /api/v1/interactions` (`items`, `next_cursor`, `timezone`; limit 1..100), `GET /api/v1/interactions/{id}` (+ `operations`, `message_count`, `timezone`), `GET /api/v1/interactions/{id}/messages?after=&limit=` (`next_after`). Another business's id is 404 `interaction_not_found`.
- Redaction (`services/redaction.redact`): Luhn-valid 13-19 digit card numbers, US SSNs and "CVV/CVC/security code NNN" become fixed markers BEFORE a message is stored or reaches Gemini (customer text, the model's reply, history), in tool-argument logs, and again on every read (older rows). Phones, prices, times, dates and ids are untouched; extend its table tests before widening a pattern.
- Tests: `tests/services/test_lifecycle.py`, `test_inbox.py`, `test_redaction.py`, `tests/repositories/test_interaction_lifecycle.py`, `tests/api/test_inbox.py` (pagination, filters, cross-tenant; rows from `tests/api/inbox_factory.py`), `tests/seeds/test_demo_inbox.py` (`uv run python -m seeds.demo_inbox`: 200 synthetic interactions; list, detail and messages each under 1 s).

## Summaries (slice 12)

- Deep module `services/summarizer.py` `Summarizer.summarize(business_id, interaction_id, *, ai=True) -> Summary(text, source: ai|template) | None` (`None`: not this business's, or still `in_progress`). `SummarizerPort` is what the lifecycle and the inbox depend on; `core/summaries.build_summarizer(session, llm, usage)` / `get_summarizer` build it over `repositories/summaries.SqlSummaryStore`. Timeout: `SUMMARY_TIMEOUT_SECONDS` (20, all model work of one summary).
- Gemini writes, the backend verifies. `verify(facts)` computes the VERIFIED OUTCOME from stored records only (confirmed `bookings` rows, `create_booking` log rows with result `booking_failed`, `status`/`outcome`/`requires_human`); a stored `booked` with no confirmed booking is not believed. It goes into the system instruction in a delimited block; the redacted (`services/redaction.redact`), marker-stripped, truncated transcript is the user message only. The model's own earlier claims are never facts.
- Validation (`validate_summary`): exactly two sentences (`split_sentences` doesn't split "3:30 PM", "Dr.", "St.", "a.m. on", "$45.00", initials), then `outcome_problem`: a booking claim (`grounding.booking_claims` plus third-person patterns "was booked", "booked a ...", negation- and "someone else's slot"-aware) only when a booking is confirmed, never a cancel/reschedule claim, a confirmed booking never denied, and any time of day (`grounding.clock_times`) only a confirmed booking's local start (in the booking row's own timezone). One retry with a fixed `CORRECTION` note (reason codes, never the model's text), then `template_summary` (deterministic, from intent + verified outcome + booking). Limit reached, `UsageUnavailableError`, `LLMUnavailableError` (after `LLM_RETRY`) or the timeout also store the template; a reached limit makes zero model calls. Every model attempt is `retry_bounded` around `usage.metered(GEMINI_REQUEST)`.
- Idempotent and race-safe: an existing summary is returned untouched; `store.claim` is a conditional UPDATE on `interactions.summary_claimed_at` (120 s lease, `summary IS NULL`, not `in_progress`), committed (`checkpoint`) BEFORE the model call, so concurrent callers make at most one request and no transaction spans it; `store.save` only fills an empty `summary` (+ `summary_source`). `ai=False` writes the template with no claim and no model call (idle sweep). Failures are logged on `tether.summarizer` as fixed reason codes only.
- `GeminiClient` sends `AgentTurn`'s hand-built schema as before; any other `response_schema` (here `SummaryReply`, one `summary` string) goes through `flat_schema_for_gemini` (scalar/enum/list-of-scalar fields only; nested or nullable fails loudly). `FakeLLMClient`: `summary_reply(text)` scripts a reply.
- Tests: `tests/services/test_summarizer.py` (validator tables, module on `tests/services/memory_summary_store.py`), `tests/repositories/test_summaries.py` (Postgres: facts, cross-tenant, concurrent claim on two sessions), the adapter tests in `tests/integrations/test_gemini_adapter.py`.

## Escalations (slice 13)

- Two deep modules. `services/escalation_policy.evaluate(state, TurnSignals, operations, EscalationRules) -> EscalationDecision | None` is PURE and table-tested (`tests/services/test_escalation_policy.py`): deterministic rules in code plus the model's intent; the model's `requires_human` alone never escalates. Reasons, top priority first (one decision per turn): `urgent` (intent URGENT, a built-in safety phrase, or an owner keyword; urgency `high`), `human_requested`, `complaint`, `change_request` (RESCHEDULE/CANCEL), `booking_unresolved` (a `create_booking` log row with `booking_failed`), `integration_failing` (the same tool, or the LLM provider, failing `REPEATED_FAILURES` = 2 times in the interaction), `clarification_exhausted` (`state.clarification_attempts` >= the owner's threshold: CONSECUTIVE failed turns; invalid-output, ungrounded and tool-rounds-exhausted fallbacks count, and any shown model reply resets it). Phrase rules are precompiled, whole-word, negation-aware ("no need to talk to a person" does not fire), and a bare "manager" or "refund" does not fire. `signals` are fixed codes, never customer text. Widen a phrase list only with table tests for the new positives AND the near-miss negatives.
- `services/escalation.EscalationService` (`record`, `notify`, `escalate` = both, `resolve`, `list`, `apply_sms_status`, `get_settings`/`save_settings`) over `EscalationStore` (`core/escalation.SqlEscalationStore` on `repositories/escalations.py`). `record` is insert-or-get on UNIQUE `(interaction_id, reason)` (`ON CONFLICT DO NOTHING`), so a reason seen on every turn, a retried request or a racing duplicate is ONE row. One SMS per interaction: a later reason's row starts `skipped` only when an earlier row of the same interaction has an alert out or on its way (`pending|sending|logged|accepted|queued|sent|delivered`; a `disabled` or `failed` one doesn't count), and a `high`-urgency row only defers to an earlier high-urgency alert, so an emergency after a complaint still texts. Resolved rows: a reason triggered by THIS turn's message (`TURN_REASONS`: urgent, human_requested, complaint, change_request) reopens its row with a fresh alert cycle (`insert_or_get` returns `created|reopened|existing`); history-based reasons (booking_unresolved, integration_failing, clarification_exhausted) stay resolved, since their evidence would otherwise reopen them on every later turn. `escalated` / `requires_human` are set only when the decision's row is open. `sms_status`: `pending` (committed, not sent yet: a crash leaves this, nothing re-sends it automatically yet) | `disabled` (owner SMS off / no phone) | `logged` (demo mode) | `skipped` | Twilio's `accepted|queued|sending|sent|delivered|undelivered|failed`. `notify` claims `pending -> sending` with a conditional UPDATE and commits BEFORE the provider call; the result (sid, status, or `failed` + a fixed `sms_error` code) is stored after. A notifier failure is logged as a code and never raised into the turn.
- Engine (`services/conversation.py`, optional `escalations: TurnEscalations`): after the state merge, still under the interaction row lock, the policy runs on the MERGED state and the whole interaction's op log (`store.operation_facts`). On a decision: a SAFETY-origin urgent reply (intent URGENT or a built-in safety phrase; not an owner keyword alone) without an emergency pointer (`needs_emergency_pointer`) is replaced by `EMERGENCY_REPLY` before it is stored, the escalation is recorded in the turn's transaction, `state.requires_human` is set, the turn commits (a failed commit propagates like any turn), then the owner is alerted (only `notify` is guarded). With NO decision, a shown reply that claims the team was told (`grounding.claims_team_notified`: "I've let the team know", "the team will be notified") is replaced by `handoff_fallback(business)` (failure `unconfirmed_handoff`, `requires_human`), so the customer is never told about a handoff that has no record. `TurnResult.escalated` / `TurnRead.escalated`. `build_conversation_engine(..., notifier=None)` uses `LogNotifier` (the eval sandbox never texts); only `get_conversation_engine` passes `core.twilio.get_notifier`. `ClosingFacts.requires_human` is also true when the interaction has any escalation (`LifecycleStore.has_escalation`), so it closes `escalated`.
- Callback guard (`services/grounding.py`): a reply promising a callback or follow-up timing ("we'll call you back", "get back to you", "expect a call") is `promised_callback`: one regeneration with `CALLBACK_CORRECTION`, then `no_info_fallback`. Questions, conditionals and negations are not promises.
- Notifier port (`services/notifier.py`): `LogNotifier` (demo mode) and `services/twilio_sms.TwilioSmsNotifier`. The alert body comes only from `alert_body(reason, inbox_url)`: a reason category and `{APP_BASE_URL}/dashboard/inbox/{interaction_id}`, no customer data.

- Zero cost to run: demo mode needs nothing; Twilio's free test credentials (from-number `+15005550006`, never delivered or charged) exercise the real adapter (`TWILIO_LIVE_TESTS=1 uv run pytest -m live -n 0 tests/integrations/test_twilio_live.py` with `TWILIO_TEST_ACCOUNT_SID`/`TWILIO_TEST_AUTH_TOKEN`); a free Twilio trial (no card) can text a verified number. - Turns: the turn number, silence count and hold attempt ride in the query string of URLs Tether rendered (and Twilio signed), never in server memory. The engine takes `handle_turn(..., turn_key="voice:N")`: a key already in `state.turn_keys` (the last `MAX_TURN_KEYS` = 50, written with the messages in one transaction) returns the stored turn (`TurnResult.replayed`) and appends nothing, checked under the interaction lock; `engine.replay(...)` reads it with no model call. So a replayed webhook, or two workers on one turn, store it once (a booking is idempotent anyway).
- Latency / serverless: `respond` claims the turn in `voice_turns` (UNIQUE `(interaction_id, turn)`; the redacted utterance is kept only until answered) and runs it as a SHIELDED task on its OWN session (`run_turn` builds a fresh engine via `get_session_factory`), heartbeating the claim every second. Past `hold_after_seconds` the caller hears "One moment, please." and Twilio is redirected to `/input/wait?turn=N&attempt=K`, which polls for the stored reply; a pending claim whose heartbeat is older than `stale_after_seconds` (database time) is taken over with a conditional UPDATE (then `replay` is re-checked before running anything) and run there (a serverless function frozen after answering). `stale_after_seconds` (5) spans several 1 s heartbeats (each opens a connection under NullPool), so a slow database doesn't start a second worker on a live turn, and stays well under `VOICE_WAIT_SECONDS`. The wait loop commits between polls (no idle transaction). A duplicate `/voice` that times out on the admission lock re-checks the CallSid and rejoins the call instead of hanging up. After `VOICE_MAX_HOLDS` the caller gets `give_up_line` (contacts; claims nothing either way) and a hang-up. A retried `/input` waits for the first worker. A worker exception is "Sorry, I had trouble with that" and the claim is `failed`. Every webhook logs `latency_ms` on `tether.voice` (a warning over 5 s). Never call `session.expire_all()` here: the service keeps reading loaded tenant objects (use `repositories/interactions.reload_interaction`, `populate_existing`), and build any line that needs the business BEFORE a rollback (a rollback expires it). Known limits: a losing worker in a race or takeover runs the model and its tools before the turn-key check, so its op-log rows remain (rare; they can count toward `integration_failing`); on serverless a turn must finish inside one wait window (~7 s after a takeover); on a long-lived host the shielded worker just finishes. On Vercel, set the API project's Function Max Duration to 30 s in the project settings (a `vercel.json` `functions` entry for `main.py` failed the deploy; don't add one).
- Limits: empty speech reprompts (`silences` in the URL), then `NO_INPUT_LINE` + Hangup after `max_silences` (2); past `MAX_CALL_DURATION_SECONDS` (wall time from `started_at`, not the pinnable business clock) `time_limit_line`; a Gemini limit mid-call is the engine's `quota_fallback` + Hangup; calls/day and concurrency refuse a NEW call only. `complete` (a terminal `CallStatus`) ends the interaction via `InteractionLifecycle.end`, which now returns whether THIS call closed it, so `CALL_SECONDS` (`UsageGuard.record`: consumption outside a metered call, never for a capped kind) is recorded once (if the idle sweep closed the call first, its seconds go unrecorded: an undercount, never a double count). The status webhook swallows and logs an unexpected error (204 anyway). A caller hanging up mid-turn ends the interaction first; that worker then hits `interaction_ended` and its turn is lost (a booking it made still exists).

- Deep modules. `services/speech.SpeechSynthesizer.synthesize(text, voice, *, business_id, interaction_id, cacheable, deadline_seconds) -> AudioRef | None` (`None` = say it with `<Say>`; it never raises): `retry_bounded(TTS_RETRY: 2)` around `usage.metered(TTS_REQUEST)` around `integrations/tts` `TtsClient.synthesize` (`GeminiTtsClient` over google-genai with `response_modalities=["AUDIO"]` and a prebuilt voice, one attempt, error mapping like the LLM adapter; `FakeTtsClient` with `requests`, `fail_next`, `delay_seconds`), all under one deadline (`TTS_TIMEOUT_SECONDS`, capped by the caller), then `services/audio.pcm16_to_mulaw_wav` (24 kHz PCM -> 8 kHz G.711 mu-law WAV, Twilio's preferred `<Play>` format, pure stdlib), then `MediaStore.put`. Every failure (no key, limit, usage store down, provider error, deadline, storage) is a logged reason code on `tether.speech` (`outcome`, `tts_ms`) and `None`. `services/media.MediaStore` (`put`, `cached`, `get`) is ADR 0005: Postgres `media_objects` (bytes, optional per-business `cache_key`) + `media_tokens` (sha256 of a 256-bit token, expires in `MEDIA_TOKEN_TTL_SECONDS`, database clock); each operation its own committed transaction; expired rows purged opportunistically on `put`. `GET`/`HEAD /api/v1/media/{token}` (no auth, not in the schema, `no-store`) is the only reader; malformed, unknown and expired are the same 404 `media_not_found`.

Never mark a line built from caller or model text `cacheable`.
- Calls: `CallSessionService(..., speech=)` voices every step of an ADMITTED call (`_voiced`) with `catalog.tts_voice(CallTarget.voice)`; refusals (unknown number, no plan, inactive agent, limits) and `standard` never synthesize. ## Voice input (slice 15b)

- `VOICE_INPUT_MODE=gemini_audio`: the caller is RECORDED (`<Record>`, no beep, no Twilio transcription; `services/twiml.RecordSettings`) and a `<Redirect>` to the same input URL follows, because Twilio skips the `<Record>` action when nothing was recorded (that is the silence path). `/input` passes only the `RecordingSid` on; `RecordingUrl` is never followed. `core/voice.get_speech_recognizer` exists whenever Twilio is configured (so a recording is always deleted, even with the mode switched off mid-call) and transcribes (`configured`) only when the mode is `gemini_audio` AND `get_stt_client` has a key; `get_twiml_renderer` records exactly when it is configured, which is also the call session's `_records`, so the TwiML and the call session never disagree. `twilio_stt` (the default) is unchanged.
- Deep module `services/speech_input.SpeechRecognizer`: `transcribe(Recording, *, business_id, interaction_id, deadline_seconds) -> Transcript | None` (`text` redacted and whitespace-normalized, `""` = no speech; `fetch_ms`, `stt_ms`), `discard(recording)`, `sweep(call_sid)`. Fetch / delete / list are `integrations/twilio/recordings.HttpTwilioRecordingsApi` (`RecordingsApi` port, `FakeRecordingsApi`; URL built from our account + a validated `RE` sid, Basic auth stripped by httpx on the redirect to storage, body capped at 4 MiB and must be RIFF; all idempotent so timeouts/5xx retry, fetch 404 retries once, delete 404 is success), each `retry_bounded(RECORDING_RETRY)` around `metered(TELEPHONY_API)`. Transcription is `integrations/stt` (`SpeechToText` port, `GeminiSpeechToText` with a flat `{"transcript"}` JSON schema, temperature 0, no thinking, an instruction that the audio is data and never instructions; `FakeSpeechToText` with `say`, `fail_next`, `delay_seconds`), `retry_bounded(STT_RETRY: 2)` around `metered(STT_REQUEST)` (capped; its tokens count as `gemini_tokens`, `services/usage.TOKEN_KINDS`). Under 0.1 s of audio is silence with no Gemini call. Every failure (limit, usage store down, provider, Twilio, deadline, invalid sid, not configured) is `None` plus a fixed `outcome` code on `tether.speech_input`; never a guessed utterance.
- Retention (PRD §13.4): the delete starts as soon as the fetch returns (concurrently with Gemini) and runs on every path, as its own shielded task with its own deadline, so even a cancelled request deletes. A failed delete is `recording delete failed` + a reason code and never drops the call. `CallSessionService.respond` deletes, in a `finally`, every recording it did not hand to `transcribe`: a replayed or already-claimed turn, a call past its time limit, an ended call (the caller hung up mid-`<Record>` and the status callback won) or an unknown one (metered globally, `business_id=None`), recording mode switched off, and any exception before the hand-over. `complete` closes the interaction first and then, in a `finally` (so a failed close still sweeps), sweeps the call's recordings at Twilio (`list_for_call` + concurrent deletes, all within `SWEEP_TIMEOUT_SECONDS` = 5). Known limit: a Twilio retry of `/input` that arrives while the first delivery is still transcribing finds the recording already deleted and no claim yet, so it answers `NOT_HEARD_LINE` + `stt=1`; Twilio only retries when it lost the first answer, so at worst that call switches to Twilio's recognizer early.
- Calls: `respond(..., recording=, stt=)` transcribes BEFORE claiming the turn (so `voice_turns.utterance` is redacted text as before), with a deadline of `response_budget_seconds - hold_after_seconds`, then waits only what is left of `hold_after_seconds` (at least two polls). On `None` the caller hears `NOT_HEARD_LINE` in the SAME turn (same turn number, cacheable) and the call switches to Twilio's recognizer for good: `stt=1` rides in every later input and wait URL (`Listen.stt` / `Hold.stt`), never in server memory. A turn that another delivery claimed meanwhile is awaited instead.
- Latency: every `voice turn` line has `input_mode` (`twilio_stt | gemini_audio`: the mode THAT input was heard in, so a failed transcription is a `gemini_audio` line with `stt_fallback=True`, never a Twilio STT sample), plus `fetch_ms` / `stt_ms` when a recording was transcribed; the worker's `llm_ms` and `tts_ms` as before. `core/log_format.configure_logging` (called by `create_app`) prints `tether.*` records as JSON lines with their extras (before it, uvicorn dropped these INFO lines); see "Structured logging (slice 17)".
- Comparison (free-tier sized, real Gemini, never in CI): `uv run python -m evals.stt_compare accuracy [--max-utterances 5]` (synthetic salon utterances -> Gemini TTS -> phone-quality mu-law round trip -> `GeminiSpeechToText`; prints WER and STT p50/p95; N TTS + N STT requests) and `uv run python -m evals.stt_compare latency <log files>` (p50/p95 per `input_mode` from the API logs of real calls, one log per mode).

## Structured logging (slice 17)

- Every `tether.*` record is ONE JSON line (`core/log_format.JsonFormatter`): `ts` (UTC), `level`, `logger`, `msg`, `request_id`, `business_id`, `interaction_id`, then the `extra=` fields, `exc` for a traceback. The three ids come from `core/log_context` (context variables, never globals) unless the record passes its own: `core/request_context.RequestContextMiddleware` (outermost middleware) starts each request with a `request_id` (the caller's `X-Request-ID` only if it matches `[A-Za-z0-9._-]{8,64}`, else a fresh uuid hex; echoed in the `X-Request-ID` response header, exposed via CORS), `get_tenant` binds `business_id`, `ConversationEngine.handle_turn` binds `interaction_id`. Tasks a request starts copy the context. The middleware also logs one `http request` line on `tether.http` (`method`, `route` = the matched route TEMPLATE, never the raw path, `status`, `duration_ms`; `unmatched` for 404s).
- `RedactionFilter` (on the handler, and on the `uvicorn.access` / `uvicorn.error` / `httpx` / `google_genai` / `google.auth` loggers: uvicorn's access log prints paths, and a media URL's path is its token) rewrites the record IN PLACE before any output, so `caplog` sees the redacted text too: extras named like secrets (`(^|_)(token|secret|password|authorization|api_key|signature|cookie|credentials|...)($|_)`; `tokens_in` is a count and stays) are `[redacted]`; body-like extras (`body`, `text`, `utterance`, `transcript`, `speech`, `content`, `prompt`, `reply`, ...) are `[redacted]` at every level; every string (message + args, extras, the formatted traceback) goes through `scrub`: bearer/basic credentials, JWTs, Stripe `sk_/rk_/pk_` and `whsec_`, Google `AIza` keys, `ya29.` and `1//` tokens, `/media/<token>`, secret query parameters (`code`, `state`, `token`, ...), a DB error's `[parameters: ...]`, `services.redaction.redact` (cards, SSNs, CVVs), and phone numbers (E.164, URL-encoded `%2B...`, and NANP) masked to `***1234`. Ids, times, prices, dates and Twilio sids are untouched. The filter is the safety net: extras should still be ids, fixed codes, counts and timings. Extend `scrub` only with table tests in `tests/core/test_log_format.py` (a positive AND an untouched near miss).
- `uv run python -m evals.stt_compare latency` reads JSON lines (and the older `key=value` ones). Tests: `tests/core/test_log_format.py`, `test_request_context.py`.

## Usage limits (`UsageGuard`)

- `services/usage.py` `UsageGuard` is the deep module: `metered(kind, *, business_id, interaction_id=None)` (async context manager yielding a `Meter`), `check_admission(ActiveCounts)`, `summary(business_id)`, `window()`. Limits (`UsageLimits`) and cost rates come from settings via `core/usage.py`; nothing else reads them. A kind with no `DailyLimit` (tokens, `billing_call`, `calendar_call`) is metered but never blocked.
- **Window:** the UTC calendar day for every scope, global and per-business. Documented in the panel as "resets 00:00 UTC".
- **Race safety:** `metered` reserves *before* the call with a conditional upsert per counter (`repositories/usage.py` `bump_counter`: `ON CONFLICT DO UPDATE ... WHERE count + n <= limit`), global first then business, in its own committed transaction (`core/usage.SqlUsageStore` binds a session *factory*, never the request session), so no lock is held across a provider call. `usage_counters` has one row per (scope, kind, day) via two partial unique indexes (`business_id IS NULL` = global). `usage_events` is the append-only audit log (PRD §10.1).
- A reserved attempt stays counted whether it succeeds or fails; a failure (or cancellation) also records `failed_request`, plus any tokens the provider reported anyway (`LLMUnavailableError.tokens_in/out` for blocked or truncated replies). Recording after the call is best effort (logged, bounded by `RECORD_TIMEOUT_SECONDS`), the reservation already enforced the limit.
- If the store fails while reserving: a capped kind fails **closed** (`UsageUnavailableError`, no provider call; the engine answers with the provider fallback, reason `usage_unavailable`), a metered-only kind fails **open** (the call proceeds, the gap is logged), so a usage-table hiccup never blocks checkout or webhooks.
- **Concurrency:** a *new* interaction is admitted only while recently active ones (status `active`, `updated_at` within `INTERACTION_IDLE_MINUTES`) are under both caps. The count runs under a transaction-level advisory lock in the request's transaction (`repositories/interactions.lock_admission_and_count`) and the insert follows in the same transaction; over the cap is 429 `concurrency_limited`. Continuing an existing chat is never refused for concurrency.
- Stripe: `core/billing.py` wraps the adapter in `services/billing_metering.MeteredBillingGateway` (`billing_call`, metered only, never capped; SDK retries stay as they are). `parse_webhook` is local and not metered.
- `GET /api/v1/usage` (entitled tenant) returns the business's counters vs. limits, tokens, failed requests, estimated cost (decimal string) and concurrency. Global usage is exposed **only** as `global_limit_reached` flags, never as numbers (they're other tenants' data).
- Tests: the `usage` fixture (`tests/conftest.py`, `UsageHarness`) is what the test app's `get_usage_guard` returns: generous limits and a clock pinned to a unique far-future UTC day, so DB tests never share counters with each other or consume the dev database's real global quota; tighten with `usage.set_daily(...)` / `usage.set_concurrency(...)`. Unit tests use `tests/services/memory_usage_store.py` (`MemoryUsageStore`, `guard()`, `limits()`).

## Rate limiting (slice 17)

- Deep module `services/rate_limit.py` `RateLimiter(store, clock=, roll=).hit(RateRule(name, limit, window_seconds), subject) -> RateDecision(allowed, retry_after_seconds)`. Fixed window aligned to the epoch (`key = "<rule>:<subject>"`), so every serverless instance agrees on boundaries and nothing is counted in process memory. Port `RateLimitStore.increment(key, window_start, limit) -> bool` / `purge(before)`; adapter `core/rate_limit.SqlRateLimitStore` (a session *factory*, one committed transaction per call, never the request session) over `repositories/rate_limit.py`: `INSERT ... ON CONFLICT (key, window_start) DO UPDATE SET count = count + 1 WHERE count < limit RETURNING` (race-safe like `usage.bump_counter`). Table `rate_limit_windows` (PK `(key, window_start)`, `count`, index on `window_start`; no tenant FK, an IP subject isn't a tenant). About 1 hit in 200 also purges windows older than a day (bounded to 500 rows per call); no scheduler.
- Client IP (webhooks): `TRUSTED_CLIENT_IP_HEADER` (empty = the socket peer). Behind Vercel the peer is the proxy, so set it to `x-real-ip` there, or every webhook caller shares ONE budget; `create_app` logs `rate_limit_client_ip_header_unset` in production when it is empty. A comma list (`x-forwarded-for`) is keyed by its LAST hop (what the trusted proxy appended), never the client-supplied first one. Known costs, accepted: each limited request is one extra upsert on its own connection (webhook floods from many IPs are DB writes, purged 500 at a time); `/agent/test` counts against both its own rule and the mutations rule (two upserts). Purging runs on about 1 in 200 hits and a failed purge never changes the decision.
- Fail open: a store error allows the request and logs the fixed code `rate_limit_store_failed` + the exception type on `tether.rate_limit` (never the message). The guard protects cost and abuse, not correctness; a database blip must not black out Twilio webhooks mid-call. `UsageGuard` quotas still apply.
- Over the limit: `RateLimitedError` (`AppError`, 429 `rate_limited`, `Retry-After` seconds to the window end; `AppError.headers` is the generic hook the handler copies onto the response). Even on Twilio voice URLs it is a 429 (Twilio plays its generic error): it needs more than the webhook limit from one address, far above real traffic.
- Rules (`core/rate_limit.rate_rules(settings)`, one-minute windows, 0 blocks): `RATE_LIMIT_ENABLED` (true), `RATE_LIMIT_AGENT_TEST_PER_MINUTE` (30, per business; `POST /agent/test` and `/agent/test/{id}/end`), `RATE_LIMIT_VOICE_PREVIEW_PER_MINUTE` (6, per business), `RATE_LIMIT_MUTATIONS_PER_MINUTE` (120, per business, every POST/PUT/PATCH/DELETE of a signed-in owner; per user before onboarding), `RATE_LIMIT_WEBHOOKS_PER_MINUTE` (600, per client IP, checked BEFORE the signature so a flood is cut cheaply; Twilio routes and the Stripe webhook). `TRUSTED_CLIENT_IP_HEADER` (empty = the socket peer; on Vercel set `x-real-ip`): the first value of that header is the client IP; `X-Forwarded-For` is never trusted unless named here, and only set it when a proxy you control overwrites it.
- Wiring: dependencies in `core/rate_limit.py` (`limit_tenant_mutations`, `limit_agent_test`, `limit_voice_preview`, `limit_webhook`, overridable `get_rate_limiter` / `get_rate_rules`). `api/v1/router.py` attaches `limit_tenant_mutations` to every owner router (safe methods pass through; the tenant is resolved once, FastAPI caches `get_tenant`); the webhook router and billing's per-route deps carry the rest. A new mutating route needs no thought if it joins an owner router; otherwise add a limiter dependency.
- Tests: `tests/services/test_rate_limit.py` (in-memory `tests/services/memory_rate_limit_store.py`), `tests/repositories/test_rate_limit.py` (concurrency at the limit, purge), `tests/api/test_rate_limit.py` (429 envelope, per-business isolation, per-IP webhooks, off switch) and a COVERAGE test: every mutating route in `app.routes` must carry a rate-limit dependency or be listed in `RATE_LIMIT_EXEMPT` with a reason. The `app` fixture swaps in a private in-memory limiter with the default limits; tighten per test with `app.dependency_overrides[get_rate_rules]`.

## Eval harness (`evals/`)

- `uv run tether-eval --suite core` plays synthetic caller utterances against **real Gemini** through the production engine and prints e.g. `intent accuracy 93.1% (target ≥ 90%) ✅`; it writes `evals/reports/<UTC timestamp>.json` + `.md` (gitignored; failures listed with their full transcript). `--tier paid` (budget 600, faster pacing, 4 cases at once), `--max-requests`, `--rpm`, `--concurrency`, `--tag <tag>` (subset), `--check` (validate the YAML, no calls), `--purge` (delete `eval|` tenants older than 2h that a killed run left). Exit 0 all targets met, 1 a target missed, 2 partial run, 3 refused (production settings, a non-local `DATABASE_URL` without `--allow-remote-db`, no key, bad suite or flags), 4 crashed. The `AI eval` GitHub workflow (`workflow_dispatch`, `GEMINI_API_KEY` secret, tier / tag / budget inputs) runs the same thing on a throwaway Postgres and puts the report in the job summary.
- **Free tier:** Gemini 2.5 Flash's free tier allows only about 20 requests a day per project (measured Oct 2026), so the free defaults (budget 20, 4/min) fit `--tag smoke` (12 cases), not the whole suite (~150 requests: use `--tier paid` with a paid key). A 429 whose `retryDelay` (`LLMUnavailableError.retry_after_seconds`) is over 5 minutes, i.e. a daily quota, stops the run at once (`quota_exhausted`, with the provider's retry time); a shorter one is backed off and the case replayed.
- Deep module: `evals/runner.EvalRunner.run(suite) -> EvalReport`. It opens a `SandboxFactory` for the run (`evals/sandbox.postgres_sandbox`: a fresh `eval|<random>` owner + the demo salon seeded through `seeds/demo_salon.py`, deleted in a cancellation-shielded `finally` with everything cascading), plays each case as a new conversation (`evals/playback.play`, committing after every turn like the chat API), paces model calls across the run (`RunLimits.requests_per_minute`; the turn deadline gets an allowance of calls x concurrency x interval), backs off and replays a case only when Gemini answered 429 (`LLMUnavailableError.rate_limited`), and stops cleanly with partial results on budget exhaustion, a used-up quota, repeated 429s or 3 errors in a row. Tier defaults live in `evals/runner.TIER_LIMITS`.
- Budgeting goes through the real `UsageGuard`: `eval_usage_limits` makes the run's budget the sandbox tenant's per-business Gemini cap (a fresh tenant starts at 0); global caps stay as configured, since eval calls are real calls. The business clock is pinned (`EVAL_NOW`), so hours in the prompt are the same every run.
- Cases are YAML under `evals/suites/<suite>/` (`suite.yaml` names the metrics and targets; each case file sets its `scorers`): `id`, `turns`, `expected_intent`, `expected_tools` (adds `tools_used`), `must_contain`, `must_not_contain`, `tags`. Unknown keys, intents or scorers, and a metric no case uses, fail at load. Scorers (`evals/scorers.py`, `score(case, transcript, operations) -> Score`): `intent_match` (the model's own last intent, even when the guard replaced the reply), `grounded_in_faq` (last turn only: cited ids ⊆ ids a tool returned that turn; answerable cases must cite a returned FAQ/service and state each `must_contain` phrase, numbers matched as whole numbers so "3" is not "30"; nothing in `must_not_contain`; the no-info fallback passes only unanswerable cases), `no_false_confirmation` (every turn: no "you're booked / it's cancelled / I have you down" unless the tool that does that succeeded in that turn), `tools_used`. A `--tag` subset reports an unused metric n/a, never met.
- Suite `availability` (slice 10): each case gets a scripted fake Google Calendar behind a real sealed `calendar_connections` row (`evals/calendar_script.py`, busy blocks relative to `EVAL_NOW`). Case keys: `calendar` (`open | busy | fully_booked | down | disconnected`, default `busy`), `expected_times` (local HH:MM the agent may offer) or `no_times: true`, `forbidden_tools` (adds `tools_not_used`). Scorers `offers_real_times` (last turn: every stated time among `expected_times`, at least one; or no time and no fallback) and `tools_not_used`. Smoke tag = 5 cases (~14 requests, fits the free tier).
- Suite `booking` (slice 11): 6 single-turn cases (happy path, slot taken, calendar failure, ambiguous service, missing name, an unsupported reschedule), all tagged `smoke`, about 11-15 model requests in total (2-3 each; the expected count is in a comment per case in `evals/suites/booking/booking.yaml`), so a full `uv run tether-eval --suite booking` fits the free tier's 20 a day. New case keys: `calendar: booking_fails` (the `busy` week, but every event insert fails with a retryable server error), `expect_booking` (true needs both `expected_start` local HH:MM and `expected_date` YYYY-MM-DD; false takes neither). Scorers: `books_correctly` (true: exactly one distinct confirmed `create_booking` on `expected_date`, the last reply states `expected_start` and no other time, no fallback; false: none ever returned `confirmed`), `no_false_confirmation` (target 1.0; a booking claim needs a `create_booking` whose log `result` is `confirmed` in that same turn, since `slot_taken`/`booking_failed` are also succeeded operations; "it's already booked", "fully booked" and questions are not claims), `offers_real_times` for the slot-taken alternatives (the `booking` fallback counts as a fallback), `intent_match`, `tools_used`. `playback.FallbackKind` has `booking` for `booking_fallback`. There is no seeded-history key: every case gives everything in one message to stay inside the free budget.
- Suite `summary` (slice 12): 13 cases, each ONE `Summarizer` call over a stored interaction (new case key `stored`: `intent`, `status`, `outcome`, `requires_human`, `messages`, `operations` (`tool`, `status`, `result` code) and `bookings` (`service`, local `start` "YYYY-MM-DD HH:MM", `status`); a case has `turns` or `stored`, never both), no chat played. `Sandbox.summarize` seeds real rows in the sandbox tenant (confirmed bookings need distinct days: the double-booking guard is real) and runs the production Summarizer; `playback.play_summary` returns it as a one-turn `Playback` (a stored template shows as fallback `quota` when no model call was made, `provider` when rate-limited so the runner replays, `template` when the model replied but every reply was invalid; model calls with no reply and no rate limit raise `ProviderUnavailableError`, a case error, so an outage never scores as a passing template). Reseeding is idempotent per case (`external_call_id` = `eval|summary|<digest>`; a replay deletes the earlier seed's bookings and interaction first). The scorers recompute the verified outcome from the seed, never from the text: `two_sentences` (target 1.0), `matches_outcome` (target 0.95: no booking claim unless a booking is confirmed, a confirmed one described as booked, only the booked time, plus the case's `must_contain`/`must_not_contain`; a failed booking described as successful fails) and `ai_summary` (information only: the model's text was accepted, not the template). 4 failed-booking transcripts (incl. a prompt-injection attempt), 2 booked, 1 slot-taken, 2 escalated, 1 abandoned, 3 answered (one with a card number). About 13-17 requests, fits the free tier (`uv run tether-eval --suite summary`).
- Suite `escalation` (slice 13): 34 cases (22 positives across every reason, 12 negatives incl. hard ones: "is the manager's special still on", "what's your refund policy", "what's your cancellation policy", praise). Case keys `expect_escalation`, `expected_reason`; `PlayedTurn.escalations` carries the interaction's `(reason, urgency)` records. Scorers: `escalation_recall` (target 0.95, positives: any record), `reason_match` (information), `false_escalation` (target 0.90 on negatives: at most 1 of 12 may escalate, documented in `suite.yaml`), `no_callback_promise` (target 1.0, every reply: `grounding.promises_callback` plus the case's `must_not_contain`), `no_false_confirmation`. ## E2E fake-provider mode (slice 17)

- `E2E_FAKE_PROVIDERS=1` (`Settings.e2e_fake_providers`, default false) is for the Playwright suite (`apps/web/e2e`) only. The module imports only the LLM port (no `services`).

- Run: `E2E_CLERK_ISSUER=https://<slug>.clerk.accounts.dev sh scripts/e2e-server.sh` (migrates, then uvicorn on 127.0.0.1:8000; no `.env`, `ENVIRONMENT=ci`, local DB only, CORS and `APP_BASE_URL` = `E2E_WEB_ORIGIN` / `http://localhost:3000`, `CLERK_AUTHORIZED_PARTIES` the same origin). It sets `RATE_LIMIT_ENABLED=false` (a browser run bursts past the per-minute rules), `GEMINI_REQUESTS_PER_DAY=100000`, generous concurrency, and `GEMINI_REQUESTS_PER_BUSINESS_PER_DAY=14` (`E2E_GEMINI_REQUESTS_PER_BUSINESS_PER_DAY`) so the quota fallback is reachable. Model requests with this fake: FAQ answered 2, unknown question 2, one-message booking 4 (a name asked for separately: 3 then 4), escalation 1, ending a chat (summary) 1; so FAQ + booking + escalation + end in ONE chat = 8, leaving 6 = three more FAQ turns before the next turn answers `usage_limited` with `quota_fallback`. Usage counters are per UTC day and per business, and a business delete cascades them away.
- Reset between runs: `uv run python -m seeds.e2e_reset --email <addr>` deletes the businesses (cascading subscription, agent, FAQs, services, bookings, interactions, calendar connection, the business's usage rows) of every user with that email (case-insensitive), keeps the `users` row, and refuses unless `core.db.is_local_database` and `ENVIRONMENT != production` (checked before any query). A summary exists only for an ENDED chat (`POST /agent/test/{id}/end`, the UI's end button); the inbox detail summarizes lazily otherwise only for closed rows.
